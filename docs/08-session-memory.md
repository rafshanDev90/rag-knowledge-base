# Phase 8 — Session Memory and Compaction

File: `server/src/services/sessionService.ts`

---

## 1. Why memory is hard

An LLM call is stateless: it only knows what is in the prompt. A conversation needs previous turns, but the context window is finite. You cannot keep appending forever.

This project uses the standard two-tier approach:

```
recent turns      → kept verbatim (sliding window)
older turns       → summarized into a running summary
```

The prompt is then:

```
[system: summary of older conversation]
[system: RAG instructions + retrieved context]
[recent user/assistant messages]
[new user question]
```

---

## 2. Session identity

```ts
getOrCreateSession(sessionId, tenantId, userId)
```

- `sessionId` is a UUID generated by the client (`crypto.randomUUID()` in the CLI) or by the controller if absent.
- `findOne({ sessionId })`; if missing, create with `tenantId` and `userId`.
- The session is the unit of memory. A new session starts with no history and no summary.

**Bug:** lookup is by `sessionId` only. It does not check `tenantId` or `userId`. Anyone who knows a session ID can continue that conversation.

---

## 3. The sliding window

```ts
const recentMessages = await ChatMessage.find({ sessionId })
  .sort({ createdAt: -1 })
  .limit(WINDOW_SIZE)      // 10
  .lean();

recentMessages.reverse();  // back to chronological order
```

- `WINDOW_SIZE = 10` messages (not turns; a user + assistant pair is 2 messages).
- Newest-first query + reverse is the standard way to get "last N in chronological order" efficiently with an index on `(sessionId, createdAt)`.
- `.lean()` returns plain objects, faster and lighter than Mongoose documents.

The window is the **short-term** memory. It is verbatim, so it preserves exact wording, numbers, and references.

---

## 4. The running summary

```ts
if (session.runningSummary) {
  messages.push({
    role: 'system',
    content: `Summary of previous conversation: ${session.runningSummary}`,
  });
}
```

The summary is **long-term** memory. It is compressed, so it loses detail but survives beyond the window.

Order matters:

1. Summary system message (old context).
2. Recent messages (recent context).
3. New user query.

This gives the model a coarse-to-fine view of the conversation.

---

## 5. `getContextForLLM` ordering detail

```ts
messages = []
if (summary) messages.push(summary system message)
recentMessages.forEach(push)
messages.push({ role: 'user', content: newQuery })
```

At the call site in `chatController`:

```ts
const messages = await getContextForLLM(session, query);
messages.unshift({ role: 'system', content: systemPrompt });
await saveMessage(sessionId, 'user', query);
```

So the final order is:

```
system: RAG instructions + retrieved context
system: summary of older conversation
user/assistant: last 10 messages
user: current query
```

Two important details:

- The current query is **not yet saved** when context is built, so it is not duplicated in the window.
- The RAG system prompt is prepended with `unshift`, so it is the very first message. That is good for instruction priority, but it means the prompt prefix changes on every query (because the retrieved context changes), which limits prompt-cache reuse.

---

## 6. Saving messages

```ts
export const saveMessage = async (sessionId, role, content, sources?) => {
  await ChatMessage.create({ sessionId, role, content, sources });
  await ChatSession.updateOne({ sessionId }, { $set: { updatedAt: new Date() } });
};
```

- Every turn writes one user message and one assistant message.
- The assistant message stores `sources` (the chunks used), which is useful for audit and future UI.
- The `updateOne` on the session is redundant because the schema already has `timestamps: true`, but it is harmless.
- Saves happen **after** `res.end()` in the chat path. If the DB write fails, the user already has the answer and nothing retries the write.

## 7. Compaction — the algorithm

`compactHistory(session)` runs after every answer:

```ts
const totalTokens = session.summaryTokenCount +
  (await ChatMessage.find({ sessionId }).lean())
    .reduce((acc, msg) => acc + enc.encode(msg.content).length, 0);

if (totalTokens > MAX_CONTEXT_TOKENS) {   // 3000
  const oldMessages = await ChatMessage.find({ sessionId })
    .sort({ createdAt: 1 })
    .limit(20)
    .lean();

  const textToSummarize = oldMessages.map(m => `${m.role}: ${m.content}`).join('\n');
  const summaryText = await generateText(prompt);   // deepseek-r1:8b

  const newSummary = `${session.runningSummary}\n${summaryText}`.trim();

  await ChatSession.updateOne({ sessionId }, {
    $set: {
      runningSummary: newSummary,
      summaryTokenCount: enc.encode(newSummary).length,
    },
  });

  await ChatMessage.deleteMany({ _id: { $in: oldMessages.map(m => m._id) } });
}
```

Step by step:

1. Count tokens: summary + **all** messages in the session.
2. If over 3000, take the **oldest 20** messages.
3. Summarize them with a separate model (`deepseek-r1:8b`).
4. Append the new summary to the old one.
5. Delete the summarized messages.

The intent is correct: keep the prompt under budget while preserving the gist.

---

## 8. Why this implementation is risky

### 8.1 It scans the whole session every turn

```ts
await ChatMessage.find({ sessionId }).lean()
```

No limit, no projection. Every request tokenizes every message in the session. Cost grows linearly with conversation length, and the result is thrown away unless compaction triggers.

Better: maintain a running token counter on `ChatSession`, update it on each save, and only query when it crosses the threshold.

### 8.2 It can summarize recent messages

`limit(20)` is not "all but the last 10". If the session has, say, 12 messages and exceeds 3000 tokens, it fetches **all 12** (the limit is 20), summarizes them, and deletes them. The sliding window then has nothing left. The model only sees the summary.

The correct slice is "oldest messages, stopping before the last `WINDOW_SIZE`".

### 8.3 The summary grows without bound

```ts
const newSummary = `${session.runningSummary}\n${summaryText}`;
```

Each compaction appends. Repeated compactions can make the summary itself large, eventually consuming the budget it was meant to save. A good summary should be **rewritten**, not appended, with a target length.

### 8.4 It is not atomic

Two concurrent requests can both read the same state, both summarize, and both delete. There is no lock, no version check, no transaction. The result can be duplicated summaries or lost messages.

### 8.5 It uses a reasoning model on the hot path

`deepseek-r1:8b` is a reasoning model. It is slow and it is **5.2 GB**. Loading it can evict the chat model on a 12 GB GPU, so the **next** user turn pays a cold start. Compaction should use the chat model (or a tiny model) and run in the background.

### 8.6 Token counting is approximate

`js-tiktoken` with `cl100k_base` is OpenAI's tokenizer. Gemma and Qwen use different tokenizers. The 3000-token budget is therefore approximate; leave headroom.

Useful rule of thumb: 1 token ≈ 4 characters of English. 3000 tokens ≈ 12,000 characters.

---

## 9. Worked budget example

Suppose:

- System prompt + 3 chunks: ~1500 tokens.
- Each message: ~150 tokens average.
- Window: 10 messages → ~1500 tokens.
- Summary: ~300 tokens.

Total ≈ 3300 tokens. With `MAX_CONTEXT_TOKENS = 3000` counted only over summary + messages (not the system prompt), compaction triggers when summary + messages exceed 3000. The actual prompt can be larger than 3000 because the system prompt is not counted.

This is a subtle mismatch: the budget variable is **history-only**, but the model's context includes the system prompt and retrieved chunks. A real budget should count the whole prompt.

---

## 10. What a better design looks like

1. Store `tokenCount` per message at write time; keep a running total on the session.
2. Compact only when the **full prompt** (system + chunks + history) exceeds a model-specific budget.
3. Summarize only messages older than the sliding window.
4. Rewrite the summary to a target token length (e.g., ≤400 tokens), not append.
5. Run compaction asynchronously, after the response, in a queue.
6. Use the chat model or a small model, never a separate 8B reasoning model.
7. Use a DB transaction or a per-session lock.
8. Keep the last N turns verbatim even after compaction.
