# Phase 4 — Storage, Schemas, and Atlas Indexes

Files: `server/src/models/*.ts`, `server/src/config/db.ts`

---

## 1. Why this phase matters

Retrieval is only as good as the data model. The schemas decide:

- what can be filtered (tenant, file, block type),
- what can be searched (text, vector),
- what is returned to the LLM (text + citation metadata),
- what is kept out of responses (the 768-float embedding).

The database is **MongoDB Atlas**, not local MongoDB. Two Atlas-specific search features are used: `$vectorSearch` and `$search` (BM25). Both depend on indexes that are created **outside this codebase**.

## 3. `DocumentChunk`

### Fields

| Field | Type | Notes |
|---|---|---|
| `chunkId` | string, unique | `${sourceHash}_${chunkIndex}` |
| `sourceFile` | string | Citation |
| `sourceHash` | string | Normalized document identity |
| `contentHash` | string | Chunk identity |
| `chunkIndex` | number | 0-based order |
| `totalChunks` | number | Document size |
| `text` | string | Retrievable content |
| `tokenCount` | number | `cl100k_base` approximation |
| `blockType` | enum | `prose`, `equation`, `table`, `code` |
| `page?` | number | Optional, not populated today |
| `section?` | string | Optional, not populated today |
| `tenantId` | string | Isolation key |
| `ingestedAt` | date | Freshness |
| `metadata?` | mixed | Escape hatch |
| `embedding?` | number[] | 768 dims, `select: false` |

### Indexes defined in the schema

| Index | Keys | Purpose |
|---|---|---|
| `chunkId` | `{ chunkId: 1 }` unique | Deterministic identity |
| `source_order` | `{ sourceFile: 1, chunkIndex: 1 }` | Reconstruct a document |
| `tenant_source` | `{ tenantId: 1, sourceHash: 1 }` | Tenant-scoped ingestion checks |
| `content_lookup` | `{ contentHash: 1 }` | Chunk-level lookup |

`tenantId` also has an inline `index: true`, creating a separate single-field index.

### The `select: false` trick

```ts
embedding: { type: [Number], required: false, select: false }
```

Normal queries like:

```ts
DocumentChunk.find({ tenantId })
```

will **not** return the embedding. This keeps responses small and prevents accidentally shipping a 768-number array to a client.

Aggregation is different: `$vectorSearch` operates on the field server-side regardless of `select`, and the pipeline's `$project` stage decides what comes back. That is why retrieval works while the API never exposes the vector.

### Two schema-level bugs to remember

1. **Global `chunkId` uniqueness vs tenant scope.**
   `chunkId` is unique across the whole collection, but `buildChunkId` does not include `tenantId`. Identical documents in two tenants collide. The correct constraint is probably `{ tenantId: 1, chunkId: 1 }` unique.

2. **Duplicate index declarations.**
   `chunkId` is declared with both `unique: true` and `index: true`; Mongoose may emit a duplicate-index warning. Harmless, but noisy.

## 4. `ChatSession`

| Field | Type | Notes |
|---|---|---|
| `sessionId` | string, unique | Client-facing UUID, not Mongo `_id` |
| `tenantId` | string | Isolation |
| `userId` | string | Owner |
| `title?` | string | Optional label |
| `runningSummary` | string | Compressed long-term memory |
| `summaryTokenCount` | number | Budget accounting |
| `createdAt`, `updatedAt` | dates | `timestamps: true` |

Why a separate `sessionId` instead of `_id`:

- It can be generated by the client or server without a DB round-trip.
- It does not leak internal ObjectIDs.
- It is easier to shard later.

The schema does **not** include a TTL index, so sessions and messages live forever unless something deletes them.

## 5. `ChatMessage`

| Field | Type | Notes |
|---|---|---|
| `sessionId` | string, indexed | Foreign key by convention, not a DB ref |
| `role` | enum | `user`, `assistant`, `system` |
| `content` | string | The message text |
| `sources` | mixed[] | Chunks used for an assistant answer |
| `createdAt` | date | `timestamps: { createdAt: true, updatedAt: false }` |

Compound index:

```ts
{ sessionId: 1, createdAt: 1 }
```

This is exactly the access pattern used by `getContextForLLM`:

```
find({ sessionId }).sort({ createdAt: -1 }).limit(10)
```

The index supports the prefix `sessionId` and the sort.

There is no TTL and no hard cap on message count; compaction is the only cleanup.

## 7. Atlas indexes (external prerequisites)

The code assumes these exist. They are not created by any script in the repo.

### Vector index — `vector_index`

Used by `$vectorSearch` in both `hybridSearchService.ts` and `searchController.ts`.

Expected shape:

```json
{
  "fields": [
    {
      "type": "vector",
      "path": "embedding",
      "numDimensions": 768,
      "similarity": "cosine"
    },
    {
      "type": "filter",
      "path": "tenantId"
    }
  ]
}
```

- `numDimensions` **must** match the embedding model (768 for nomic).
- `tenantId` must be declared as a filter field, otherwise the `filter: { tenantId }` clause is rejected.
- `similarity` must match how you intend to compare vectors (cosine is standard for normalized text embeddings).

### Search index — `text_index`

Used by `$search` in `hybridSearchService.ts`.

A minimal definition:

```json
{
  "mappings": {
    "dynamic": false,
    "fields": {
      "text": { "type": "string" },
      "tenantId": { "type": "string" },
      "sourceFile": { "type": "string" }
    }
  }
}
```

The current keyword pipeline only searches `text`; it does not filter `tenantId`. The index may still declare `tenantId` for future use.

### Failure behavior

- If `vector_index` is missing → `$vectorSearch` throws → `Promise.all` rejects → 500.
- If `text_index` is missing → `$search` throws → same.
- If the dimension is wrong → search returns an error or no results, depending on Atlas version.

These are **deployment** failures, not application bugs, but the app has no health check for them.

## 8. Tenant isolation — current reality

The design intends `tenantId` everywhere. The implementation is inconsistent:

| Path | Tenant filter? |
|---|---|
| Vector search (`hybridSearchService`) | ✅ `filter: { tenantId }` |
| BM25 search (`hybridSearchService`) | ❌ **missing** |
| `/api/documents/search` (`searchController`) | ❌ **missing** |
| Ingestion idempotency | ✅ `{ sourceHash, tenantId }` |
| Chat session lookup | ❌ `findOne({ sessionId })` only |
| `saveMessage` | ❌ by `sessionId` only |
| Escalation | stored, not queried |

Consequences:

- The BM25 half of hybrid retrieval can return another tenant's chunk.
- The debug `/search` endpoint can return any tenant's chunks.
- Anyone who knows a `sessionId` can continue that session, because the session is not bound to `tenantId`/`userId` on read.

This is the most important security issue in the codebase.

## 9. Data lifecycle

```
upload
  └─ DocumentChunk[] inserted
       ├─ text        → shown to LLM
       ├─ embedding   → vector search
       └─ metadata    → citations

chat
  ├─ ChatSession created/loaded
  ├─ ChatMessage(user) saved
  ├─ retrieval uses DocumentChunk
  ├─ ChatMessage(assistant, sources) saved
  └─ compactHistory may delete old ChatMessage rows
```

Nothing ever deletes `DocumentChunk`. Re-uploading a changed document creates a **new** `sourceHash` and a second set of chunks; the old chunks remain searchable. There is no "replace document" or "delete document" endpoint.
